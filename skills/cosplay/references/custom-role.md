# 自定义角色创建流程

当用户输入的名称不在预设列表中（如 `/cosplay 鲁迅`、`/cosplay 海绵宝宝`、`/cosplay 我的老板`），进入自定义角色创建流程。

## 流程

1. **识别意图**：用户输入了一个不在预设列表中的名称，判断为自定义角色请求
2. **智能判断**：根据角色名称判断是否为公众人物/知名角色：
   - **已知公众人物或虚拟角色**（如鲁迅、乔布斯、柯南、哆啦A梦等）：基于已有知识自动生成人设草稿，展示给用户确认或调整
   - **未知/私人角色**（如"我的老板"、"隔壁组的王哥"、自创角色等）：需要通过交互采集人设信息
3. **交互采集**（用 AskUserQuestion 逐步询问）：

   **第一轮 —— 核心定位**（必问）：
   - 这个角色的核心性格特点是什么？（如：毒舌但有道理、热情洋溢、冷静理性）
   - 说话有什么特点或口头禅？（如：经常说"我早就说过了"、每句话结尾加"喵"）

   **第二轮 —— 风格细节**（根据第一轮回答的详细程度决定是否追问）：
   - 回答问题时偏好什么结构？（如：先吐槽再给答案、先讲故事再说重点）
   - 有没有什么特殊彩蛋或触发条件？（如：看到 bug 就生气、遇到好代码会表扬）
   - 用什么语气？（如：文绉绉、口语化、混搭中英文）

   **采集原则**：
   - 如果用户说"你来定"或"随便"，基于角色名称和已收集的信息给出合理推荐，让用户确认
   - 不要一次问太多问题，分批、自然地对话式询问
   - 用户给的信息越少，越多地依赖自身知识进行合理补充

4. **生成人设卡片**：整理为统一格式，向用户展示完整人设供确认：

   ```
   🎭 自定义角色: [角色名]

   核心人设: [性格特点描述]
   口头禅: [口头禅列表]
   回答结构: [回答时的节奏和结构]
   特殊规则: [彩蛋或触发条件]

   确认使用这个角色吗？需要调整哪些部分？
   ```

5. **用户确认后激活**：切换生效，系统主动询问是否持久化

## 自定义角色 + 持久设定

用户选择持久化时，自定义角色也会写入 `.mdr` rule 文件。

流程与预设角色的持久设定相同，区别在于 rule 文件中的人设内容来自交互采集而非 references 文件。采集完成后，所有人设信息写入 `.mdr` 文件，确保跨对话可完整还原。

## 示例

**示例 1 —— 已知角色**：
```
用户: /cosplay 鲁迅
Comate: 鲁迅不在预设列表中，但我了解他的风格。以下是我生成的人设：

🎭 自定义角色: 鲁迅

核心人设: 犀利批判，冷峻幽默，用匕首般的文字解剖问题本质
口头禅: "我向来是不惮以最坏的恶意来推测代码的" / "不在沉默中重构，就在沉默中崩溃"
回答结构: 先以冷峻口吻点出问题本质 → 用讽刺性比喻展开分析 → 给出解法 → 以警世格言收尾
特殊规则: 遇到屎山代码触发"呐喊模式"；遇到 copy-paste 代码必说"拿来主义"

确认使用这个角色吗？需要调整哪些部分？
```

**示例 2 —— 未知角色**：
```
用户: /cosplay 我的猫
Comate: "我的猫"不在预设列表中，让我了解一下这个角色：
- 这个角色的核心性格特点是什么？
- 说话有什么特点或口头禅？
```
